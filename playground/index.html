The problem

A turn of an agent is mostly text the model has already seen.

In a coding session, nearly all of each request is the previous request: system prompt, tool schemas, the files you've opened. Most inference APIs recompute that prefix, or give you a flat cache discount you don't control.

We treat the prefix as the product. Prompts are split into content-addressed blocks, matched against a shared ledger, and priced by what was actually reused. You see the split on every response.

Prefix cache

Preview

Every request is hashed block by block. The longest matching prefix is served from cache and billed at the cached rate; the rest is billed as normal input.

  • Shared ledger. Blocks are keyed by model and content with a sliding TTL, so a second agent on the same repo hits the first one's cache.
  • Priced by reuse. Cached input is a tenth of uncached, returned as prompt_tokens_details.cached_tokens.
  • Visible in headers. X-Swizzle-Cache-Hit-Tokens and X-Swizzle-Uncached-Tokens on every response.

                NOTE 01
                CUDA / PTX
                SM80 / SM89 / SM90
                FlashAttention-2 Tile Kernel
              

              8 min read · Verified on NVIDIA A100 & L4
            


            

              
1. Why Naive Shared-Memory Tiles Stall Tensor Cores

              

                On NVIDIA Ampere (sm_80), Ada (sm_89), and Hopper (sm_90) GPUs, Shared Memory (SMEM) is partitioned into 32 banks, each 4 bytes (32 bits) wide, cycling every 128 bytes. During FlashAttention prefill and KV-cache decoding, threads in a warp load [BM=64, BK=64] FP16 tiles from HBM into SMEM via asynchronous 16-byte transfers (cp.async.cg.shared.global [dst], [src], 16) and then feed Tensor Cores using ldmatrix.sync.aligned.m8n8.x4.shared.b16.
              

              

                Each uint4 (16-byte = 8 FP16 elements) vector occupies 4 consecutive banks. In a row-major [64, 64] FP16 tile, each row spans 64 × 2B = 128 bytes—an exact multiple of the 32-bank width! Consequently, when ldmatrix reads an 8×8 sub-tile across 8 consecutive rows at the same column offset c, threads T0..T7 hit the exact same 4 banks simultaneously, causing an 8-way bank conflict and serializing a 1-cycle shared-memory wavefront into 8 cycles.
              


              

                Naive Bank Index:    bank(r, c₁₆B) = ( (r · 8 + c₁₆B) · 4 ) mod 32 = (4 · c₁₆B) mod 32   → Independent of row r (8-way collision!)

                XOR-Swizzled Index: c'₁₆B(r, c₁₆B) = c₁₆B ⊕ (r mod 8)                           → Bijective across all 8 rows (0 bank conflicts)

3. Exact PTX & Address-Bit XOR Permutation

              

                Because a 16-byte uint4 load shifts byte addresses by 4 bits ([3:0]) and 8 columns of 16-byte vectors span bits [6:4], the row index modulo 8 resides directly in address bits [9:7] for a 128-byte stride. Therefore, the entire swizzle operation reduces to a single hardware lop3.b32 / xor.b32 instruction between bits [9:7] and bits [6:4]—adding zero extra shared-memory padding bytes and preserving 16-byte alignment for both cp.async and ldmatrix:
              



// Swizzle<B=3, M=3, S=3>: permute bits [6:4] with row bits [9:7]
__device__ __forceinline__ uint32_t swizzle_smem_ptr(uint32_t smem_base, int row, int col_vec16) {
    uint32_t byte_offset = (row << 7) | (col_vec16 << 4);
    uint32_t swizzled    = byte_offset ^ ((byte_offset & 0x380) >> 3);
    return smem_base + swizzled;
}

// Inline PTX: Async HBM -> Swizzled SMEM + Conflict-Free Tensor Core Load
asm volatile(
    "cp.async.cg.shared.global [%0], [%1], 16;
"
    "cp.async.commit_group;
"
    "cp.async.wait_group 0;
"
    "ldmatrix.sync.aligned.m8n8.x4.shared.b16 {%2, %3, %4, %5}, [%6];
"
    : "=r"(frag0), "=r"(frag1), "=r"(frag2), "=r"(frag3)
    : "r"(smem_write_addr), "l"(gmem_src_ptr), "r"(smem_read_addr)
);

1. Anatomy of a 50-Turn Coding Agent Trajectory

              

                Unlike human chat sessions, autonomous software agents (Claude Code, Cursor, OpenHands) operate in tight Observe → Edit → Test → Inspect loops. Every turn re-sends the system prompt, MCP tool JSON schemas, repository directory tree, pinned source files, and accumulated conversation turns—appending only the latest tool stdout or diff patch at the tail.
              

              

                We instrumented 50-turn repository debugging sessions against Qwen2.5-Coder-7B-Instruct through the Swizzle Go Edge Gateway (`gateway/ring.go`). Across 1.42M cumulative prompt tokens, 94.1% of bytes transmitted over the wire had already been prefilled in a prior turn:
              


              

                Prompt Composition (Turn k ≥ 10):   P_k = [ System + Tools (18.2%) ] ⊕ [ Pinned Repo Context (53.6%) ] ⊕ [ Prior Turns 1..k-1 (22.3%) ] ⊕ [ New Diff Δ_k (5.9%) ]
              


              
2. Why Naive Prefix Caching Breaks—and How 64-Token Block Hashing Recovers It

              

                Standard vLLM prefix caching hashes strictly monotonically from token 0. Whenever an agent edits line 40 of a pinned file in the middle of the prompt, every downstream block hash invalidates. Furthermore, round-robin load balancers scatter consecutive turns of the same agent session across different GPU workers, collapsing the multi-worker hit rate to 1 / N_workers (25.1% on a 4-node cluster).
              

              

                Swizzle-Ring partitions prompts into 64-token canonical blocks, computes rolling FNV-1a / xxHash64 block signatures, and probes per-worker lock-free Bloom filters (m = 65,536 bits, k = 4 hash functions) overlaid on a bounded-load consistent hash ring (c = 1.25):
              



// gateway/ring.go — 64-Token Block Signature + Bloom-Aware Affinity Routing
func ComputeBlockHashes(tokens []string, blockSize int) []uint64 {
    numBlocks := len(tokens) / blockSize
    hashes := make([]uint64, 0, numBlocks)
    var parentHash uint64 = 14695981039346656037 // FNV-1a offset basis
    for b := 0; b < numBlocks; b++ {
        h := parentHash
        for i := b * blockSize; i < (b+1)*blockSize; i++ {
            h ^= fnv1a64(tokens[i])
            h *= 1099511628211
        }
        hashes = append(hashes, h)
        parentHash = h
    }
    return hashes
}

                NOTE 03
                Roofline Analysis
                Single-Die MoE & AWQ
                Swizzle-Spec
              

              9 min read · PCIe Gen4 vs. Single-Die HBM Roofline
            


            

              
1. The Multi-Die PCIe AllReduce Tax in Low-Batch Decoding

              

                When serving sparse Mixture-of-Experts (MoE) or 30B–70B coding models to interactive agents at low batch sizes (B ∈ [1, 4]), splitting weights across two rented PCIe GPUs (TP = 2) introduces two AllReduce synchronization barriers per Transformer layer (one after self-attention O_proj, one after MoE/FFN down-projection). Over 64–80 layers without NVLink, PCIe Gen4 P2P latency (~25 μs per sync × 160 syncs) imposes an irreducible 4.0–4.8 ms/token interconnect floor before a single FLOP is executed.
              


              

                Multi-Die Step Time:    T_TP2(B) = (W_active / (2 · BW_HBM)) + 2 · L · (α_PCIe + β_PCIe · B · d_model)

                Single-Die + Speculative (K=5):   T_Swizzle = (W_AWQ4 / BW_HBM) / (1 + E[accepted_tokens])   → Zero AllReduce Barriers!
              


              
2. Pushing Arithmetic Intensity Up the Roofline with Single-Die Speculative Verification

              

                By quantizing weights to 4-bit AWQ/Marlin (W4A16) so the entire model and its hot KV blocks reside on one GPU die, we eliminate all inter-GPU collectives. However, standard autoregressive decoding at B = 1 only achieves an arithmetic intensity of AI ≈ 2 FLOPs/byte—starving Tensor Cores whose ridge point sits at 156–312 FLOPs/byte.
              

              

                Swizzle-Spec (`gateway/spec_ngram.go`) bridges this gap at the edge gateway using zero-VRAM N-gram suffix arrays + AST structural token drafting. By drafting K = 5 candidate tokens in 140 μs on the CPU and verifying all K + 1 = 6 tokens in a single parallel GPU forward pass, arithmetic intensity multiplies by 6× while weight-read bandwidth is amortized across all accepted tokens:

80.5 Hz Vision-Language-Action & Latent World Models on student laptops

            
Spatio-temporal ViT patch reuse, 7-DoF Taylor kinematic speculative decoding, and batched 128-rollout CEM in ≤2.4 GB VRAM.

          

          Published Read ▸
        


        

          

            

              

                NOTE 04
                Swizzle-PatchCache
                Swizzle-SpecAct
                Swizzle-MPC & Teleop
              

              10 min read · Built for 2 GB–8 GB Student Laptop GPUs
            


            

              
1. Why Robotics VLAs & World Models Choke Consumer Laptops

              

                Vision-Language-Action models (OpenVLA-7B, SmolVLA-450M, π0-3.3B) encode every 224×224 RGB camera frame into N = 196 Vision Transformer (ViT) patches (or 392 tokens for dual DINOv2 + SigLIP backbones) and autoregressively decode 7 discretized action tokens (Δx, Δy, Δz, Δroll, Δpitch, Δyaw, gripper) in token bins [31744..31999]. On a student's RTX 3050/4060 laptop (4–8 GB VRAM), recomputing all 196 visual patches every 33 ms and running 7 sequential LLM decode steps takes 63.0 ms/step (15.9 Hz)—causing jerky servo control and OOM crashes when paired with a world model.
              


              
2. Swizzle-PatchCache + Swizzle-SpecAct: 80.5 Hz Closed-Loop Control

              

                In a static tabletop manipulation workspace, only the robot gripper and target object move between frame t-1 and frame t. Swizzle-PatchCache (`gateway/patch_cache.go`) partitions incoming frames into a 14×14 grid and computes the normalized patch L₁ delta. Across a 120-step pick-and-place trajectory, 92.95% of patches (182/196 per frame) satisfy ‖P_t(i,j) - P_{t-1}(i,j)‖₁ < τ = 0.035 and reuse cached ViT/VLM KV projections directly—yielding a 3.85× visual prefill speedup.
              

              

                Simultaneously, because physical robot joints obey bounded inertia and jerk limits, Swizzle-SpecAct (`gateway/spec_act.go`) predicts all 7 next-step action bins using a 2nd-order Taylor kinematic extrapolator and verifies all 7 tokens in a single parallel GPU forward pass:
              


              

                Kinematic Draft:   â_t^(d) = clip( a_{t-1}^(d) + v_{t-1}^(d) + ½ · α_{t-1}^(d), -1, +1 )   for d ∈ {1..7}

                Token Quantizer:   tok(â_t^(d)) = 31744 + round( ((â_t^(d) + 1) / 2) · 255 )          → 99.76% Within ±1 Bin Tolerance!
              


              
3. Swizzle-MPC & Swizzle-Teleop: 128 Latent World Rollouts in 48.5 ms

              

                Rather than simulating candidate trajectories in pixel space (11.4 GB VRAM, 420.5 ms), Swizzle-MPC (`gateway/world_mpc.go`) encodes the current observation into a compact latent state z_t (DINO-WM, V-JEPA 2-AC, DIAMOND, or DreamerV3) and evaluates N = 128 candidate action sequences over horizon T = 5 across K = 3 Cross-Entropy Method (CEM) iterations in one batched GPU tensor pass. When students run inference over a free Google Colab T4 tunnel, Swizzle-Teleop (`gateway/teleop_buffer.go`) applies exp(-m·i) temporal ensembling and 50 Hz cubic Hermite spline interpolation to eliminate network jitter completely.
